Wantzel

A programming language for the code AI agents write.

Strict, so wrong programs do not compile. Fast, so an agent can build on every change — and so fifty of them can build at once. Zero dependencies: one static binary, nothing to install, nothing to isolate.

Pointing an agent at it

A model has not seen this language in training, so you hand it the specification. That is practical here because the specification is small: 593 lines for the whole language, and another 463 on the pitfalls. Both fit in a prompt with room to spare.

The name is the idea

In 1837 Pierre Wantzel proved what cannot be done. Trisecting an angle with compass and straightedge, doubling a cube — people had tried for centuries, and he showed it is impossible. Not "not managed yet". Impossible.

That is what a compiler should do: say what cannot work, before you find out the hard way. It sounds like a limitation and it is the opposite. A proof that something is impossible is liberating — you stop looking, and the time you would have spent on a dead end goes to the road that does exist.

An agent that does not know something is impossible keeps searching. It writes something plausible, gets a vague error, tries a variation, builds a workaround — and sometimes produces something that runs, until one day it does not.

Why

You are shipping code you did not write and have only partly read. Nobody can tell by eye whether a conversion is safe or an index can run past the end — and plausible code is exactly what a generator is good at producing.

So the compiler has to hold what a careful author used to hold. That changes the question a language should be answering. Not what makes this pleasant to write? but what makes a wrong program impossible to compile, and a right one fast to arrive at?

A compact, fast, strict language, fit to be used in iterations when agents write the code.

Every decision in Wantzel is weighed against that sentence, and each word of it settles something. Compact, so the whole specification can be read in one sitting rather than consuming an agent's attention. Fast, so a loop can afford to compile on every single change — which is what makes iterating possible at all. Strict, because what the compiler refuses is what nobody has to review. And in iterations, because the unit of work is not a program written once, but a cycle run many times, where every signal is read by a machine before a human sees it.

What that buys you

Run a thousand agents on the machine you already have

Fifty agents each compiling the entire compiler finish in 352 ms wall clock and peak together under 100 MB. Not fifty containers, fifty virtual environments or fifty package caches — fifty processes. Your fleet size stops being a budget question about RAM and disk, and a compile becomes cheap enough to put inside the loop rather than at the end of it.

All fifty produced byte-identical binaries. Under that load, that is the other half of the story: when agents build the same source, any difference between their outputs is a real difference and never a race.

Spawning a subagent costs almost nothing

The reason agents are usually rationed is not the model — it is what each one drags along. A worktree, a package install, a virtual environment, a container to keep it from touching the others. Every extra agent is a minute of setup and a few hundred megabytes, so you think twice before starting one.

Here a workspace is a directory with source files in it, and the toolchain is a single 514 kB binary that every agent shares. Nothing to install per agent, nothing to isolate them from each other, nothing to tear down afterwards. Fifty compiling at once peaked under 100 MB together — about two megabytes each.

That changes what you are willing to try. Spawning ten agents to attack a problem from ten angles stops being a decision about infrastructure and becomes a decision about whether the idea is worth ten attempts. Throwing nine of them away costs nothing, and being able to throw work away cheaply is most of what makes the approach work.

Fewer tokens burned getting to a build that works

Every failed compile is a round trip: the error goes back into the context window, the model rewrites, you pay for both. So the cost of a coding agent is not really the code it writes — it is the number of attempts, and how much each attempt has to read.

Two things shorten that. The specification is small enough that consulting it does not eat the context. And every message names the file, the line, and the actual problem in plain words, so an attempt aims at the real cause instead of guessing near it.

Nothing to isolate, because nothing is shared

No package manager — so there is no mechanism by which a dependency could arrive. No runtime on the target, no container to describe that runtime, no lockfile, no virtual environment keeping packages from destroying each other.

That matters more for agents than for people. The usual reason to sandbox an agent is that its build can reach out and change the machine. Here a build reads source files and writes one file. Deploying is copying that file.

Silence means correct

No warnings — only errors. A warning is an error with a grey zone around it, and grey zones do not survive contact with time: they pile up, get suppressed, and eventually nobody can tell whether a clean run means clean code or silenced noise.

Exit 0 has to be trustworthy on its own, because something machine-read acts on it without weighing tone or context. You can build a loop on that. You cannot build one on "it worked, but there were nine remarks".

An error names your source, not the compiler

A program that was simply too large once failed with an error pointing deep inside the compiler — every word of it true, and all of it aimed the wrong way. A human shrugs and looks elsewhere. A generator takes it at face value and starts rewriting code that was never the problem. Now the message names the file, the line, and the limit that was hit.

Naming the input is not politeness. It is the difference between a loop that converges and one that thrashes.

When the rules change, they change loudly

Before 1.0 the language can still change, and one thing has: the { } comment was removed in 0.2.0 because a brace inside the comment text silently turned the rest of the sentence into code. That is the distinction that matters. A change that makes the compiler refuse something needs far less justification than one that alters what working code does — because code a generator produced last week does not get reread when the rules shift underneath it. It simply starts being wrong, quietly, somewhere nobody is looking.

For the same reason Linux and Windows are kept as identical as they can be made. A person learns "on Windows this one is different" once and remembers. A generator has no such memory, and will write the Linux shape every time.

There is no layer left to misconfigure. A field that is not in the schema is not a run-time validation error — it is a program that does not compile. If you want an agent to call your backend, that is the whole of it.

What it is

A small, strictly typed, procedural language whose compiler is written in itself. It emits static x86-64 executables for Linux and Windows: no assembler, no linker, no C library, nothing to install. The compiler is one file and carries its own standard library, so the download is the entire toolchain.

program hello;
include "io.wz";
begin
  io.puts(STDOUT, "hello, world\n");
end.
  • 50 agents compiling at once — wall clock until the last one finished 352 ms
  • …their peak memory, all fifty together < 100 MB
  • Compiling the compiler with itself (6,536 lines) 11 ms
  • …and a 97,000-line program 2.2 s
  • Peak memory while compiling 2.9 MB
  • The compiler binary 514 kB
  • Full bootstrap from C to a fixed point 1 s
  • External dependencies 0

Measured on one machine, with the method in the repository — so you can check the numbers rather than believe them. Compile time is not linear in the size of the source: the rate holds at the scale the compiler itself is, and falls off well before a hundred thousand lines. That is a known defect, not a property we are defending.

Two languages shaped this one

Turbo Pascal, for what a short loop feels like. It compiled in the blink of an eye — you pressed a key and your program ran — and that speed made something possible that has been rare since: you iterated in thought rather than in waiting time. You simply tried things, because trying was free. One environment, one step, strict enough to catch your mistakes, complete enough to build a whole project with.

Then everything got slower, which is worth asking about, because computers got a thousand times faster in the meantime. The gain went into layers. The speed here is not nostalgia; it is a claim that the old loop is still available if you decline them. The syntax comes from the same place for a plainer reason: Pascal reads almost like pseudocode, and there is little to learn before you can read the standard library.

Go, for what a deployable artifact should be. A static binary with no runtime to install, fast builds, a standard library that can serve HTTP on its own rather than through a framework, and a deliberately small language that resists clever constructions. Wantzel shares all four and pushes two further, at a price Go had good reason not to pay: dependencies are not merely few but structurally impossible, and the contract for an API is a language construct rather than a generator you run as an extra build step. The price is an ecosystem of one.

Neither is a model to copy. What is taken from Turbo Pascal is the loop; what is taken from Go is the shape of the thing you ship.

And it is worth saying plainly: none of this makes it unpleasant to write by hand. The same properties are what made programming feel light before the stacks grew — you press a key and it runs, the error says exactly what is wrong and where, there is one way to express the thing, and there is no environment to set up before you start. This is not an AI-only language with humans tolerated. It is a small, fast, strict language that happens to suit a generator for exactly the reasons it suits a person.

Where this is the wrong tool

The question is not whether this is right for everyone — it is whether it fits a given job. What you give up is not little:

That is a defensible price for a program that has to keep working for years on a machine nobody maintains, where the number of moving parts matters more than how fast you write the first version. For a great deal of other work it is a bad price, and the honest answer is to use something else.

And the language is pre-1.0: anything may still change — the language, the library, the command line. The compiler compiles itself, ships a standard library and runs real programs, but the claim that a language designed for generated code actually helps generated code is a research question, not a slogan. It is being measured. When there are numbers they will be here, including the unflattering ones.

Where to go next
